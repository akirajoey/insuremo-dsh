# TASK-162/163 isolated compatibility and route regression fixture

This is a **source-runtime regression/observation fixture**, not a plugin release, full compliance gate, browser test, HMR reproduction, Windows test, rc.5 compatibility claim or real declaration-contract test. The fixture itself does not modify production source or generated artifacts; TASK-163 separately fixes route ownership in source, and tracked `git-dist` remains unchanged.

## Run

From the workbench repository root, with the existing local dependencies and a clean sibling `../deepseek-harness` source checkout at `687f282e8625c6b8d11ff58211a90524be2e4317` (H2/rc.2):

```sh
node test/compat/run.mjs
```

The runner checks H2 HEAD and tracked cleanliness without an optional Git write. The test also fails closed before runtime imports if not launched with isolated paths. It makes one new directory under the real `/tmp`, assigns separate `HOME`, `USERPROFILE`, `DSH_HOME`, and `TMPDIR`, passes a limited environment without inherited credentials, then **removes only that directory** in `finally`, including after test failure. It does not install packages, build `lib`, change the Harness checkout or write a user profile. It requires the already-available workbench `tsx`, `typescript`, `yaml`, H2 source and H2 package dependencies; missing prerequisites fail explicitly. The CLI fixture only resolves `/fixture/bin/fixture-imo`; `spawn` and jobs throw and are counted, with no real IMO/Skills execution, subprocess execution or remote network operation. Each real HTTP server binds `127.0.0.1` on an OS-assigned port and is disposed in its test.

For test-time source resolution only, the temporary config makes all existing `tsconfig.base.json` paths absolute and adds aliases to H2 sources for `cordis-plugin-loader`, `dsh-host-webserver`, `dsh-util-values`, `dsh-util-crypto`, `dsh-brand`, `dsh-typert-protocol` and `dsh-sandbox`. These avoid missing `lib/index.js` and stale built-lib/source mismatches without touching either checkout. The first test prints and asserts `import.meta.resolve` paths for Cordis, Loader, WebServer, Tools, SystemPrompt and all five extra transitive source aliases. This is **not** verification of npm dependency closure or of the real rc.2/rc.5 `.d.ts` files.

## Behavior and evidence boundaries

1. Real H2 **Loader** entries use its in-memory `cordis:` builtins containing the actual workbench source namespaces; entry configuration reads the real patch inject lists. **TASK-165 entry shape**: the insuremo-service root exports exactly one plugin shape — `default ImoCliService`; the full multi-service mount is an explicit `insuremoServiceMount` object that only the aggregate passes to `ctx.plugin`. Standalone unwrap therefore selects the default CLI, checks Config/fixture probe and unload, without assuming the other InsureMO services were mounted, and asserts no top-level `apply` exists. The builtin supplies a namespace and does **not** exercise package resolution or installation.
2. The aggregate is mounted through the real Loader, with real Cordis, WebServer, ToolRuntime and SystemPrompt. It checks its child services, eight tool registrations, health status endpoint and both absence/presence of a **fake settings face**. Storage, workspace registry, subprocess, jobs, LLM, skills, agents and directory picker are in-memory fakes. It asserts the aggregate mounts `insuremoServiceMount` and that the root exposes no second plugin shape. **Root inject single source**: `WORKBENCH_ROOT_INJECT` is the only list; a test parses `cordis.patch.yml` and requires deep equality with it and with `WorkbenchDistService.static inject` (10 services), with `systemPrompt` excluded so it stays a child dependency.
3. Without SystemPrompt, a **fake tools face** satisfies the existing aggregate patch while unrelated services remain active and the dependent tool service waits. This isolates the root/child dependency distinction; it is not a real ToolRuntime test.
4. **Historical TASK-162 direct-mount observation**: real H2 WebServer plus `ctx.plugin(InsuremoRoutesService)` served GET `/api/icomposer-workbench/insuremo/overview` as 200 `{}` after 40 ms and still 200 after `await fiber.dispose()`; same-path registration then threw duplicate. This did not establish a loader-entry or HMR leak. The TASK-163 assertion now waits for real HTTP readiness, checks the route after 40 ms, requires 404 for all thirteen owned paths after owner unload, then remounts a distinct generation. Repeated disposal of the old owner cannot remove any of the new generation's handlers. An exact-path collision must fail and leave the external handler intact.
5. Registration failure tests use a tracing/fault-injection adapter over the **real H2 WebServer table**. They inject an error within the write group before it returns its composite disposer, collide after all writes, and exercise first-route conflict and throwing rollback disposers. Every successfully acquired handler must be released in reverse; failed/colliding and unrelated external owners remain intact, original errors are propagated, and repeated disposal does not delete a later owner. The direct write-route composite is also tested for idempotence.
6. **TASK-165 child-failure observability (bounded)**: a child that fails during this mount turn is reported through the structured host log (`insuremo-service: child <label> failed: <bounded message>`), while healthy siblings keep running and the aggregate is not shut down wholesale. The mounts are not awaited, so `apply()` never stays open on a PENDING child. **Observability boundary**: only a failure observed while `mountChild`'s `await()` is settling gets the label and the 300-character truncation. Cordis `await()` on a PENDING fiber (its `inject` not yet satisfied) returns immediately because there is no in-flight transition to wait on; a child that activates later and then fails is reported by the host's own fiber error log, **without** our label and **without** our truncation — existing host behaviour, not a claim of universal observability. Tests force a real route-child duplicate (an activation-time failure), require the label `routes` record, and assert healthy siblings (`imoCli`, `imoAuth`, `imoOverview`) keep running. The aggregate root's ACTIVE state means "mount calls completed", **not** "every child is healthy"; no root-level failure propagation is claimed. A universal deferred-failure wrapper was considered and not adopted; it stays an open decision rather than an implemented guarantee.
7. A real Loader aggregate runs against the same WebServer via a generation-stamping adapter. The test waits for an actual 200/readiness before observing another 40 ms, withdraws the `webServer` dependency and requires 404, restores it and requires a new generation and 40 ms stability, then disposes the aggregate and requires 404. In a separate loader conflict, the real route child must enter FAILED and `await child.await()` must reject with the duplicate while its partial registrations roll back and the foreign owner survives. **Boundary**: aggregate `apply()` does not await that child (see item 6 — the activation-time failure is reported through the structured log; failures on later activation are not covered by that label), so the loader root can remain ACTIVE; do not claim aggregate-wide failure propagation or success. The root's ACTIVE state is recorded, not enshrined as correct. These tests cover the isolated loader/dependency lifecycle, not installed packages or full HMR.
8. Real loopback HTTP tests retain the write route's method, Origin, action-header, JSON content-type, body-size and response-header gates. The only successful write action invokes an in-memory fake upgrade face; no real command executes.
9. The actual workbench tool service registers eight tools/seven prompt sections in the real H2 registries, **exactly once**, through the public `ctx.effect` lifecycle: the registrar returns one disposer per tool/prompt, the service keeps them individually and releases them newest-first. `registerIcomposerTools` is transactional — a duplicate or thrown registration releases everything already acquired (reverse order) and rethrows the original error, so a foreign owner's registration survives. Tests cover a duplicate on the first prompt and mid-way on a tool, then assert the foreign registration is still present after the failed owner is disposed.
10. **Retained internal dependency (TASK-164/D2)**: same-turn synchronous release still relies on the existing `internal/plugin` listener. Public effect disposers only run after the unload turn yields — the effect-only control test observes a duplicate when a caller registers again immediately after `dispose()` without awaiting, and success only after the await. The workbench service therefore keeps the listener (it releases only its own single-shot handles; the later effect teardown is a no-op) and the tests assert same-turn removal plus immediate name reuse. Publicly covered instead: awaited unload, reverse release, transactional partial-failure rollback, dependency loss/restore re-registration with one generation, and repeated teardown idempotence. Removing the listener needs evidence of a public Cordis/Host API that guarantees synchronous cleanup during unload (or an equivalent pre-unload hook) **and** a real HMR/loader reload test; neither exists here, so it is not claimed as public-only or as a second accepted exception.
11. A separate effect-only fixture on the real ToolRuntime records whether a direct same-turn duplicate window is observed and requires successful registration after awaited disposal. The old H2 observation is `duplicate` before await; this is diagnostic, not an assertion that the window must remain. Neither tool test is actual HMR.
12. `EX-WH-01` uses the original SHA-256 of the whole `WorkspaceHealth.tsx` and an AST-selected, exact hash of its `sidebar.footer.action` registration. It checks preservation of observer, row selectors/placement, manual root, 60-second polling and cleanup. Any health-source hash change is a review stop; a later authorized Tooltip-localization-only change can update it **after review of the diff showing that driver/position/behavior remain unchanged**. The footer hash covers only the health registration, not other slots. Static checks do not show real icons, absence of duplicates or real unmount behavior.

The suite currently contains sixteen `node:test` tests: the TASK-163 route set, the TASK-164 tool-lifecycle set, and TASK-165 entry-shape / root-inject / child-failure-observability coverage. The accepted conflict is limited to the existing WorkspaceHealth driver, not BrandChrome, Picker, or any `internal/plugin` listener. No JSDOM/static result substitutes for a real UI test; no `cua_repl` or actual UI automation is provided here. Later UI/upgrade validation must check original-row visibility, position, no duplicates and unmount/reinstall cleanup.

An additional ad-hoc `tsc --noEmit` experiment over the source-runtime aliases did **not** pass: the mixed H2 source/dependency declaration closure reports missing or incompatible types such as `dsh-working-directory`, `dsh-ptc-runtime` and `SessionActivity`. The final run had no diagnostics directly in `baseline.test.ts`, but this is not a clean typecheck or a real H2 declaration-contract PASS; TASK-167 owns that separate gate.
