# TASK-162 isolated compatibility baseline

This is a **source-runtime regression/observation fixture**, not a plugin release, full compliance gate, browser test, HMR reproduction, Windows test, rc.5 compatibility claim or real declaration-contract test. It is deliberately separate from the tracked `git-dist`; no production source or generated artifact is changed.

## Run

From the workbench repository root, with the existing local dependencies and a clean sibling `../deepseek-harness` source checkout at `687f282e8625c6b8d11ff58211a90524be2e4317` (H2/rc.2):

```sh
node test/compat/run.mjs
```

The runner checks H2 HEAD and tracked cleanliness without an optional Git write. The test also fails closed before runtime imports if not launched with isolated paths. It makes one new directory under the real `/tmp`, assigns separate `HOME`, `USERPROFILE`, `DSH_HOME`, and `TMPDIR`, passes a limited environment without inherited credentials, then **removes only that directory** in `finally`, including after test failure. It does not install packages, build `lib`, change the Harness checkout or write a user profile. It requires the already-available workbench `tsx`, `typescript`, `yaml`, H2 source and H2 package dependencies; missing prerequisites fail explicitly. The CLI fixture only resolves `/fixture/bin/fixture-imo`; `spawn` and jobs throw and are counted, with no real IMO/Skills execution, subprocess execution or remote network operation. The one real HTTP server binds `127.0.0.1` on an OS-assigned port and is disposed in each test.

For test-time source resolution only, the temporary config makes all existing `tsconfig.base.json` paths absolute and adds aliases to H2 sources for `cordis-plugin-loader`, `dsh-host-webserver`, `dsh-util-values`, `dsh-util-crypto`, `dsh-brand`, `dsh-typert-protocol` and `dsh-sandbox`. These avoid missing `lib/index.js` and stale built-lib/source mismatches without touching either checkout. The first test prints and asserts `import.meta.resolve` paths for Cordis, Loader, WebServer, Tools, SystemPrompt and all five extra transitive source aliases. This is **not** verification of npm dependency closure or of the real rc.2/rc.5 `.d.ts` files.

## Behavior and evidence boundaries

1. Real H2 **Loader** entries use its in-memory `cordis:` builtins containing the actual workbench source namespaces; entry configuration reads the real patch inject lists. Standalone unwrap selects the default CLI, checks Config/fixture probe and unload, without assuming the other InsureMO services were mounted. The builtin supplies a namespace and does **not** exercise package resolution or installation.
2. The aggregate is mounted through the real Loader, with real Cordis, WebServer, ToolRuntime and SystemPrompt. It checks its child services, eight tool registrations, health status endpoint and both absence/presence of a **fake settings face**. Storage, workspace registry, subprocess, jobs, LLM, skills, agents and directory picker are in-memory fakes. The observed named `insuremo.apply` child is reported, not frozen as a permanent export requirement.
3. Without SystemPrompt, a **fake tools face** satisfies the existing aggregate patch while unrelated services remain active and the dependent tool service waits. This isolates the root/child dependency distinction; it is not a real ToolRuntime test.
4. A direct `ctx.plugin(InsuremoRoutesService)` test uses real H2 WebServer on loopback. With no overview service provided, GET `/api/icomposer-workbench/insuremo/overview` after 40 ms is 200 `{}`. On the original baseline, after `await fiber.dispose()` it is still 200, registering the same exact path throws duplicate, and a separately owned `/compat-unrelated` remains 200 `other-owner`. A second real-server case puts an external owner on the exact same path and confirms Workbench unload does not remove that owner's handler. Remount/collision states are printed; old `safe()` swallows duplicate errors. This is a **known open C-05 direct-mount observation**, not a claim that the loader entry or real HMR reproduces it. The test reports either residual or released behavior rather than demanding a leak forever. TASK-163 must replace the diagnostic with assertions for correct ownership/release and new generation.
5. The actual workbench tool service registers eight tools/seven prompt sections in the real H2 registries. Its current internal listener releases them in the same turn and a later awaited remount succeeds. This preserves the observed behavior, not permission to retain an internal API forever.
6. A separate effect-only fixture on the real ToolRuntime records whether a direct same-turn duplicate window is observed and requires successful registration after awaited disposal. The old H2 observation is `duplicate` before await; this is diagnostic, not an assertion that the window must remain. Neither tool test is actual HMR.
7. `EX-WH-01` uses the original SHA-256 of the whole `WorkspaceHealth.tsx` and an AST-selected, exact hash of its `sidebar.footer.action` registration. It checks preservation of observer, row selectors/placement, manual root, 60-second polling and cleanup. Any health-source hash change is a review stop; a later authorized Tooltip-localization-only change can update it **after review of the diff showing that driver/position/behavior remain unchanged**. The footer hash covers only the health registration, not other slots. Static checks do not show real icons, absence of duplicates or real unmount behavior.

The count is eight `node:test` tests (the two tool observations are separate tests). The accepted conflict is limited to the existing WorkspaceHealth driver, not BrandChrome, Picker, or any `internal/plugin` listener. No JSDOM/static result substitutes for a real UI test; no `cua_repl` or actual UI automation is provided here. Later UI/upgrade validation must check original-row visibility, position, no duplicates and unmount/reinstall cleanup.

An additional ad-hoc `tsc --noEmit` experiment over the source-runtime aliases did **not** pass: the mixed H2 source/dependency declaration closure reports missing or incompatible types such as `dsh-working-directory`, `dsh-ptc-runtime` and `SessionActivity`. The final run had no diagnostics directly in `baseline.test.ts`, but this is not a clean typecheck or a real H2 declaration-contract PASS; TASK-167 owns that separate gate.
